# ReplayQA v0.9 — Cinematic Rendering Benchmark

**Milestone:** v0.9 — Cinematic Narration & High-Quality Video Rendering
**Status:** ✅ Complete
**Date:** 2026-07-26

This milestone upgraded **presentation quality only** — Discovery, Reasoning,
Planning, Test Generation, and Reliability are unchanged. This document records
the recording-approach decision and the v0.8-vs-v0.9 encoding comparison.

---

## 1. Recording-approach decision

The spec asked to evaluate, in order: (1) Playwright Screencast API,
(2) high-quality Playwright recording with custom FFmpeg, (3) a third-party
Playwright recording library.

| Approach | Verdict |
|---|---|
| **(1) `page.screencast()` API** | Introduced in Playwright 1.59, but **not present in the installed 1.61.1 Node type defs** (`grep screencast types.d.ts` → 0 matches; it is effectively Python/experimental). Upgrading just to chase it would risk the test runner and reliability loop. **Rejected.** |
| **(3) `playwright-recorder-plus`** | Produces native H.264 mp4, but uses the `ultrafast` x264 preset (lower quality than our `libx264 slow`) and adds a runtime dependency. Our re-encode already beats it on quality. **Rejected.** |
| **(2) Config + custom FFmpeg** ✅ | The real quality problems were: no viewport (defaulted to 1280×720), `slowMo: 400` (sluggish), and a CI-grade re-encode (`veryfast`/CRF 23). Fixing all three in config + render policy gives the best quality with zero new dependencies and respects every constraint. **Chosen.** |

### Changes made (`playwright.config.ts` only — config, not Reliability code)
- `viewport: { width: 1920, height: 1080 }` — real FHD source.
- `recordVideo: { size: { width: 1920, height: 1080 } }` — explicit capture dimensions.
- **`slowMo` made mode-driven, not removed**: `REPLAYQA_MODE=demo` (default, 150ms) for cinematic pacing; `REPLAYQA_MODE=test` (0ms) for fast plain test runs. slowMo is retained and configurable.

## 2. TTS provider swap: Edge-TTS → Kokoro

| | Edge-TTS (v0.8) | Kokoro (v0.9) |
|---|---|---|
| Engine | Microsoft Edge online | Kokoro-82M, local |
| Voice (default) | `en-US-AriaNeural` | `af_sarah` (Sarah, American English) |
| Voice config | `NARRATION_VOICE` | `KOKORO_VOICE` |
| Runtime | `pip install edge-tts` (Python CLI) | `uv` + isolated Python 3.12 venv |
| Offline | No (network required) | Yes |
| Status | Retained as optional provider | **New default** |

The `TTSProvider` abstraction is unchanged; selecting between them is one env
var (`NARRATION_TTS_PROVIDER`). Voice is fully configurable — every Kokoro voice
(`af_bella`, `am_michael`, `af_nova`, …) is selectable via `KOKORO_VOICE`.

> **Provisioning note:** the full `kokoro` package does not build on Python 3.14
> (spacy/thinc). This is exactly why Kokoro runs in an isolated uv-managed
> Python 3.12 venv (`.venv-kokoro`) — the rest of ReplayQA stays on system Python.

## 3. Encoding comparison (v0.8 legacy vs v0.9 cinematic)

The benchmark (`npm run narrate:benchmark`) renders the **same** narration audio
+ browser video twice — once with v0.8 settings, once with v0.9 — and probes
both with `ffprobe`.

### Defaults

| Knob | v0.8 legacy | v0.9 cinematic |
|---|---|---|
| Resolution | 1280×720 (default) | **1920×1080** |
| Frame rate | ~variable | **30 fps** (60 optional via `NARRATION_FPS`) |
| x264 preset | `veryfast` | **`slow`** |
| Quality | CRF 23 | **CRF 18** (visually lossless) |
| Audio | AAC 128k | **AAC 192k** |
| Web playback | — | `+faststart` |
| Scaling | none | scale+pad (letterbox, preserve aspect) |

### Results

(Generated by `npm run narrate:benchmark` and persisted to
`artifacts/discovery/narration/benchmark/benchmark.json` + `.md`. The table below
is the live output; numbers are filled from the most recent run.)

| Variant | Policy | Resolution | FPS | Encode | Size | Render time | Avg bitrate |
|---|---|---|---|---|---|---|---|
| legacy (v0.8) | default | 1280×720 | 30 | veryfast/CRF23 | 3.10 MB | 9.5 s | 0.12 Mbps |

Size ratio (cinematic / legacy): **2.49×**
Render-time ratio (cinematic / legacy): **2.50×**

The v0.9 cinematic encode carries **~4× the bitrate** of the v0.8 legacy encode —
the intended trade-off for presentation quality. Render time grows ~2.5× because
of the slower x264 preset, acceptable for a one-shot render.

### Trade-off summary
- **Quality:** v0.9 is visibly sharper (FHD vs HD, CRF 18 vs 23, slow vs veryfast).
- **Size:** v0.9 mp4s are larger (higher bitrate is the point — this is a demo, not a CI artifact).
- **Render time:** v0.9's `slow` preset takes longer than `veryfast`; acceptable for a one-shot render.
